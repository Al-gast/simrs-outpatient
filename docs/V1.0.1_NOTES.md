## Implemented

1. **Session restoration:** browser-only endpoints and scoped HttpOnly, SameSite=Strict cookie; original 2h JWT expiry, no extension; token stays in memory for API requests. Boot waits for server authentication; transient outage presents retry rather than falsely logging out. Existing bearer-only clients and Node introspection unchanged. Logout clears cookie and invalidates token versions; 401 clears local session. Non-secret logout suppression marker uses localStorage only; no token or patient data stored there. Cookie shared among tabs; use separate browser profiles for independent roles. XSS can still access the explicit restore API; use HTTPS in non-local deployments. Offline logout cannot guarantee server revocation; marker prevents restoration when storage is available. Local demo HTTP only; production requires HTTPS on both frontend and API, same-site deployment, validated CSRF/CORS and security review.
2. **Master auto-code:** five new DB sequences, serialized generation and existing unique constraints, skip colliding manually supplied codes; staff prefixes D/N/S; procedure T; medicine OB; lab L; clinic POL-. Six-digit minimum, non-reused sequence numbers (gaps normal). UI auto-generates all coded masters by default, except optional clinic mnemonic; existing code displayed read-only in edit. Legacy manual API code accepted. No existing master codes updated. Migration creates sequences only and grants runtime role; rollback refused after generated numbers used.
3. **Explicit state vs delete:** master table has separate status toggle and permanent deletion, action icons with accessible labels/tooltips. PATCH only `active` for status, existing dependency guards apply. Strict `DELETE ?mode=permanent` returns conflict on referenced data/stock without modifying status. Old DELETE without mode retains existing fallback for external clients. Editing other fields no longer overwrites active flag in UI. No change to user account deletion policy.
4. **Clinical reasons:** first procedure/Rx/lab section write may omit reason, even when shared record version already >0. Subsequent saves/deletions/re-additions require reason, tracked through existing current rows and append-only audit history within locked transaction; invoice revision requires reason regardless. New advisory flags in clinical DTO drive frontend visibility. Existing record/diagnosis and stock adjustment validation unchanged. Old clients sending reason remain compatible. Existing clinical optimistic version, invoice/stock logic and lab locks retained.
