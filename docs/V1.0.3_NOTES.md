# v1.0.3 — Clinical & Billing Workflow

Baseline: exact cumulative ZIP v1.0.2. Source implementation only; combined runtime verification on MacBook deferred by user. No dependency added, no database migration added, no backend change. Prior v1.0.1 migration 000004 remains required on upgrade from v1.0.0. Existing UAT data, canonical IDs, API contracts, pricing snapshots, permissions and server-side transitions remain unchanged.

## Clinical workflow
- Doctor route `/doctor/:visitId` (numeric ID), only doctor role; server still enforces assigned visit and clinical access. Queue and history open the dedicated workspace. Browser refresh restores the session (v1.0.1) and fetches the visit again; unsaved draft and step position are not persisted.
- Five stages: record, procedures, prescription, laboratory, review. Only review exposes finish; record must be saved and all drafts clean. Successful save adopts server snapshot and advances; failure keeps draft and requires fresh data before finalization. Optional empty stages can be explicitly skipped without sending a write. Previous stage is available when no draft is dirty. Step indicator is non-clickable; review cannot be jumped to.
- Review displays persisted record, selected services and estimated costs. Finish still requires confirmation and sends original `expected_version`. Server remains authoritative; client steps are not a new API precondition. After finish, read/correction tabs preserve prior diagnosis amendment and unpaid procedure revision rules. History remains accessible independently, subject to existing API scoping.
- Dedicated workspace uses React Router data-router (existing 6.30 dependency), `useBlocker` for dirty or in-flight navigation, browser beforeunload; no dialog when clean. Explicit logout confirmation warns about unsaved work, but logout/expiry can still discard drafts. No offline draft storage. Review progress resets on reload. Lab results recorded concurrently may require reload to view latest snapshot; stale writes remain subject to server protections.

## Billing and ancillary
- `/billing/:visitId` for cashier, `/billing-monitor/:visitId` for administrator (read-only, server RBAC unchanged). Payment pending key/payload remains in sessionStorage under original key and scope. Retry, stale revision handling, overpayment checks and explicit confirmation are unchanged. Pending/unsent form navigation warns; tab-close recovery remains limited to sessionStorage. No gateway, refund or new payment semantics.
- Invoice display and print order registration → procedure → medicine → laboratory. Payment percentage uses BigInt integer arithmetic, truncated to 0.1% (not rounded up); zero-total paid invoice displays 100%. Amounts still exact, no changes to accounting.
- RX/LAB/INV/PAY display pads to minimum six digits without changing raw identifiers; exact padded invoice search is translated back to canonical API query. Report technical ID fields and audit identifiers remain raw. Current numbering schemes and original receipts in database remain unchanged.
- Pharmacy and clinical prescription show quantity unit where supplied, subtotal and total from snapshot prices; dosage/frequency remain free text (no invented unit/dosing data). Lab and prescription empty messages reflect finished visit; lab result lines preserved. Node result submission, explicit fallback and idempotency key logic untouched.
- Print document uses isolated popup, DOM text nodes, branding, A4 stylesheet, ordered lines, patient details, invoice revision, payment amounts, status and timestamps. Receipt explicitly identifies individual payment, not proof of full settlement. Browser print headers/footers cannot be disabled by application CSS reliably: turn off in print dialog. No real PDF generated here. Browser pagination, popup behavior and visual layout must be tested.
