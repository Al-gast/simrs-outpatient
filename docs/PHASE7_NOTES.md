# Phase 7 — Billing & Payment (v0.7.0-billing)

Cumulative source checkpoint based on Phase 6 ZIP. No database schema/migration, design-token or dependency changes. Package versions updated. Node continues to be read-only and lab integration service; billing writes belong exclusively to Yii.

## Implemented
- Auto invoice generation in finish-exam/last ancillary transaction, or explicit idempotent issuance for legacy ready visits. Registration fee, medical procedure, completed lab and dispensed medicine snapshots. Sequence numbers; gaps allowed. Zero total completes with no payment row.
- Cashier queue, search, filter, pagination, detail, exact integer rupiah amounts, partial/full payment, simulated cash and non-cash, individual receipts and invoice browser-print/PDF via system dialog. Admin read/print only. Print uses DOM text nodes rather than interpolated HTML, and no external assets. Patient and clinic labels are current master values (not historical snapshots); individual receipt amount/method/date/number are stored.
- Visit and invoice row locks, separate payment-key advisory lock namespace, UUID uniqueness and canonical payload hash. Same actor/key/payload returns current invoice and original payment ID before closed/revision checks. Different key represents a new intended payment. Overpayment blocked; zero balance transitions completed. Audit is in transaction with write.
- Assigned doctor can revise procedure quantities/list before first payment after all services finish. Updates clinical version, invoice lines/total/revision and audit in same transaction. Diagnosis-only changes after finish remain possible without changing costs. Revision vs payment serialized on visit row; stale revision rejected.
- Payment recovery: attempt key/body stored in sessionStorage per user/visit before sending, immutable retry while uncertain, recovery on reload/relogin in same tab. No token or patient name stored. Browser storage may still contain dummy transaction metadata until confirmation/tab close; do not use real data. If storage unavailable, new payments blocked. Closing tab, clearing storage, another browser/device, or another operator cannot guarantee same-key recovery; reconcile payment history first. No automatic retries with new keys. Distinct-key duplicate intent cannot be recognized if balance still permits both payments. No payment gateway or reconciliation with external banking.

## Verification and limitations
Actual checks: see `evidence/phase7-static-checks.txt`. PHP pure policy, TS pure policy (strict typecheck of dependency-free modules), syntax transpilation, config parsing, and ZIP checks only. Docker, PostgreSQL, Composer and installed npm dependencies are unavailable; actual SQL execution, transaction/race behavior, Yii/React/Node integration, complete TS project typecheck, build, Postman, browser printing and screenshots are unverified. `scripts/billing-smoke.py --db-check` and `postman/Billing.postman_collection.json` are provided, not executed. Existing clinical smoke updated for new post-payment lock rule. No screenshots fabricated.

Scope decisions: no cancellation/refund/void, adjustment/credit note after partial or full payment; no tax/insurance/discount; no real payment gateway; no partial dispensing; no global SPA navigation guard. Invoice line revisions stored as before/after audit snapshots, not separate historical PDF versions. Displayed invoice/receipt patient/clinic names and cashier names are current references. Invoice print reflects last loaded snapshot; refresh before printing, especially after another cashier/doctor changes it. Queue aggregates all payment rows (indexed invoice_id) and uses offset pagination; performance benchmark still pending. User administration and reporting dashboard are not implemented yet. All data dummy only, not for production medical use.
