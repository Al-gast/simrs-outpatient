# v1.0.4 — Dashboard & Administration

Baseline: exact cumulative ZIP v1.0.3. Source release candidate; browser, production builds, HTTP and PostgreSQL runtime tests deferred until final upgrade. No new dependency, endpoint, database migration, grant, or write policy. Upgrade from v1.0.0 still requires the prior v1.0.1 migration 000004.

## Dashboard
- UI-037/038: daily responsive SVG trend charts for visits and payment receipts. All dates in the selected inclusive WIB interval (max 366 days) are represented, including zero dates. Exact daily values are accessible via an expandable table; chart geometry alone uses rounded ratios. CSS donut counts invoices, not patients or Rupiah. Table provides exact status counts and outstanding values, including a neutral state when no invoices exist.
- UI-040: existing Node `/reports/summary` adds `total_amount` and `paid_amount` decimal strings to each `payments` group. Existing fields are unchanged. All three aggregates are calculated from the existing reporting.invoice_status view, in the same read-only repeatable-read snapshot as before. UI uses BigInt and refuses incomplete or inconsistent totals rather than displaying fake zero. `total_amount = paid_amount + outstanding`. No new data privilege or patient identifiers.
- Date semantics: *cash received in period* uses `paid_at` in WIB, regardless of the visit date. *Total billed, total paid, outstanding* use invoices belonging to visits dated in the selected period and all payments recorded on those invoices up to the report snapshot, including payments outside that period. This is not a historical as-of-period-end balance and cannot be computed by subtracting the cash KPI from billed cohort totals.
- UI-043: all six report metrics open centered detail modal, with current applied period, metric, optional clinic scope, pagination, error retry and close without moving to a bottom-of-page card. Draft date filters do not affect report until applied; applying a new period closes and resets details. Summary/detail are separate snapshots; concurrent writes can cause differences. Server page limit stays 10,000 and 20 rows per page UI; total shown remains actual API total. Existing read-only monitoring titles/routes retained from previous phases.

## Users
- UI-046: existing admin-only `GET /admin/users` adds nullable `staff_name` via a left join by staff ID, including inactive staff. Original DTO fields remain; mutation responses and audit projections unchanged. This avoids N+1 requests and limited-page lookup errors. Null for non-doctors; old server with missing field shows a neutral fallback, not an invented name.
- UI-047/050: create requires explicit role selection; edit, password reset, and activate/deactivate each have dedicated icon, accessible label and tooltip. Edit only changes name/role/staff; reset only password; status only active flag. All send the original full PATCH fields with expected_version; password omitted for non-password writes. Server retains self-edit refusal, immutable doctor binding, last-state checks, staff validation and token_version increment. Status actions confirm and invalidate list/audit queries. No hard-delete action.
- Password policy remains 12–72 UTF-8 bytes, unchanged from the backend; no change to authentication, session restore, RBAC or doctor identity.

## Audit log
- UI-051–057: Indonesian action/entity labels, remote searchable actor selector (name/username, includes inactive accounts; first 50 matches, refine search for more), action and entity selectors, reset to current month, responsive filter grid, and centered detail with raw actor/entity/audit IDs, code and Request ID. Dropdown values remain existing exact API filter codes. Known action codes translated; unknown codes preserved as text, selectable when present or searched by valid exact code.
- Entity is not a separate clinical department: clinical, pharmacy, lab and billing actions are stored under `visits`. The module/entity dropdown reflects that fact; use the action filter to distinguish these activities. No fictitious entity aliases. API audit projection remains unchanged; no before/after JSON, reasons, clinical contents, tokens or password hashes are exposed, including in detail modal.
