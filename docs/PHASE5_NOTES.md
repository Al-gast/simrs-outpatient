# Phase 5 — Electronic Medical Record & Medical Procedures

Version v0.5.0-clinical. Cumulative source checkpoint based on the exact Phase 4 archive. No dependency, schema, migration, Node service or approved design token change. Yii owns all clinical transactions; React uses the existing Ant Design theme, white sidebar, teal, spacious layout and responsive clinical drawer. This is a dummy-data technical test, not clinical production software.

## Implementation and decisions

- Assigned doctor starts a visit, opens the clinical drawer from queue or own visit history. Required complaint, anamnesis, physical examination, primary diagnosis, secondary diagnoses (0–10), and six numeric vital signs (systolic, diastolic, pulse, temperature, respiratory rate, weight). Validation bounds are application guardrails only, not diagnosis or advice. Free-text diagnoses, no ICD terminology lookup (not specified by test).
- Doctor saves EMR first, then selects up to 30 distinct active procedures with quantity 1–100. Yii owns name/price snapshots; existing line IDs and snapshots survive quantity change. Removing/re-adding a line intentionally creates a new snapshot. All lines validated before replacement. Integer amounts are strings in API; React uses BigInt for displayed totals. New item price preview can differ from final server snapshot if a master price changes before save.
- A single optimistic version (`medical_records.version`) covers record changes, procedures and finishing. First save expects 0, all other writes require the current version. All writes lock the visit first (procedure writes acquire master shared advisory lock before visit), validate version and state, commit clinical data and audit together. Stale writes return 409 without silent overwrite. Updates require reason. Existing policy unit tests cover branches, not actual DB locking.
- Finish requires saved record; pending lab/prescription -> services_pending, otherwise ready_for_billing. The phase cannot create prescriptions/lab orders yet. Their actual service completion and state recalculation arrive Phase 6. After finish only diagnosis corrections allowed, with reason and version. Fee-affecting edits frozen; Phase 7 must implement the designed unpaid-invoice revision path, locking visits/invoices and checking payments atomically. No invoice yet; procedure snapshots are billing inputs, not a generated bill.
- Clinical APIs are separate from administrative visit projections. Doctor role + assigned anchor mandatory. Own records are accessible; cross-doctor historical read allowed only via today's assigned in_exam visit for the same patient. Historical metadata is paginated, and detail accesses logged. No admin raw clinical audit API. Audit before/after JSON contains dummy clinical notes, restricted to core DB privileges; retention/encryption and external compliance not implemented.
- Drawer has record, procedures and clinical history tabs; loading, server error, record version, explicit reload, per-tab discard and close confirmation. Beforeunload guard protects draft on browser reload. No global SPA navigation blocker or persisted draft; session expiry/logout can discard unsaved changes. Record and procedures cannot be saved while the other tab has an unsaved draft; discard or save before switching mutation. Browser behavior not yet verified. No actual screenshots claimed.
